# Yakable PRD 规范

PRD 用来说明一个产品需求为什么做、要做什么、不做什么，以及什么情况下算完成。  
它不是技术设计，也不是开发任务清单。  
一份好的 PRD，应该让产品、开发、测试和 AI 对需求形成基本一致的理解。

## 1. 什么时候需要写 PRD

新增完整功能、独立模块、复杂流程，或者明显改变已有产品行为时，需要先写 PRD。  
如果一个需求包含多个页面、状态、角色或业务规则，也应该先通过 PRD 把边界讲清楚。  
PRD 的作用是减少开发开始以后反复猜测和重新确认。

小范围文案调整、纯样式修改、明确的 Bug 修复、只改代码结构但不改变产品行为的重构，通常不需要单独写 PRD。  
不要为了“有文档”而写文档。  
已有 PRD 已经覆盖的小改动，也不需要重新创建一份。

## 2. PRD 放在哪里

所有 PRD 统一放在：

```text
docs/prd/<domain>/
```

二级目录表示产品领域，例如 `system`、`project`、`session`。  
目录按照产品能力划分，不按照前端、后端、数据库等技术模块划分。

PRD 文件统一使用：

```text
<feature>-v<version>.md
```

例如：

```text
docs/prd/system/user-management-v1.md
```

## 3. 一份 PRD 应该写什么

PRD 至少要讲清楚六件事：背景、目标、本期范围、本期不做、功能与业务规则、验收标准。  
如果存在用户角色、状态流转、页面交互、风险或依赖，再根据实际需求补充。  
不相关的章节不要为了套模板强行保留。

推荐结构：

```markdown
# <功能名称> PRD V1

## 1. 背景
## 2. 产品目标
## 3. 本期范围
## 4. 本期不包含
## 5. 功能与业务规则
## 6. 验收标准
## 7. 后续演进
```

## 4. 背景和目标怎么写

背景只说明当前存在什么问题，以及为什么现在需要解决。  
不要一上来就写具体技术方案，也不要把实现方式当成问题本身。  
读完背景后，应该能够理解这个需求为什么存在。

产品目标描述这次需求最终想达到什么结果。  
不要写“优化体验”“更加友好”“提升效率”这类无法验证的空话。  
目标应该能够在功能完成后判断是否真正达成。

## 5. 范围一定要写清楚

“本期范围”明确这一个版本真正要完成什么。  
每一项都应该能够对应到实际产品行为，而不是对应某个类、接口或者开发任务。  
V1 优先形成最小但完整的产品闭环。

“本期不包含”同样重要。  
和当前需求有关、但这次明确不做的能力，需要直接写出来。  
不要把范围控制留给开发过程中临时判断。

## 6. 业务规则怎么写

一段只讲一个意思，一条规则只表达一个判断。  
默认值、状态变化、权限限制、数量限制、时间限制、异常和边界，都应该明确写出来。  
不能把关键规则留给开发人员或者 AI 自己猜。

规则尽量使用明确词语：`必须`、`应`、`可以`、`禁止`。  
少使用“尽量”“合理”“友好”“灵活”“相关”等模糊词。  
如果一个要求无法判断是否满足，就应该继续把它写清楚。

示例可以帮助理解，但示例不能代替规则。  
即使删除所有示例，正式规则本身也应该完整成立。  
如果规则存在例外，需要把例外条件一起写出来。

## 7. PRD 不写技术实现

PRD 负责描述 What，不负责规定 How。  
类名、方法名、Repository、Mapper、SQL、框架选择、线程模型等内容，通常属于技术设计。  
如果一个技术细节不会改变产品行为，就不应该写成产品需求。

PRD 可以描述必要的数据概念、接口契约或系统约束。  
但只写到产品需要明确的程度，不展开具体代码结构。  
产品规则和技术实现要保持边界。

## 8. 验收标准怎么写

验收标准说明什么情况下这个版本可以认为完成。  
至少要覆盖主流程、关键业务规则，以及用户真正会遇到的重要异常和边界。  
验收标准必须能够被人工验证或测试用例验证。

不要只写“功能正常”“符合预期”。  
应该明确用户做什么、系统表现成什么样、什么结果算正确。  
开发和测试应该能够基于同一条验收标准得到一致结论。

## 9. PRD 怎么更新

PRD 不是写完以后就不能修改。  
开发过程中如果产品规则发生变化，应先更新 PRD，再让代码和测试跟随新的规则。  
不能让代码成为产品规则唯一的来源。

小范围补充和澄清直接修改当前版本。  
如果产品范围、核心流程或关键规则发生明显变化，再创建新的 PRD 版本。  
已经完成的历史版本不要被改到失去原来的产品含义。

## 10. Ready 前检查

PRD 准备进入开发前，只需要确认几个问题：为什么做清楚了吗？做什么清楚了吗？不做什么清楚了吗？  
默认行为、异常和边界清楚了吗？还有没有需要开发或 AI 自己猜的地方？  
什么情况下算完成，产品、开发和测试是否能得到一致答案？

如果这些问题还回答不清楚，这份 PRD 就还没有准备好进入开发。  
PRD 不追求长，而追求确定。  
**PRD 的价值不是记录更多信息，而是减少实现时需要猜测的信息。**
