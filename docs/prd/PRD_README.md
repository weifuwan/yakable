# Yakable PRD 规范

本规范适用于 Yakable 的产品需求文档（PRD）。

PRD 的目标不是把产品写得越详细越好，而是让产品、设计、开发、测试和 AI 在进入实现前，对“为什么做、做什么、不做什么、什么算完成”形成一致理解。

> PRD 描述产品需求，不描述具体代码实现。

## 1. PRD 要回答的问题

一份 PRD 至少需要回答：

- 为什么要做？
- 要解决什么问题？
- 谁会使用？
- 本期要做什么？
- 本期明确不做什么？
- 核心流程是什么？
- 有哪些业务规则？
- 异常、边界和状态如何处理？
- 什么情况下算完成？

如果这些问题还无法回答清楚，不应该直接进入开发。

## 2. 什么情况需要 PRD

以下场景应优先编写 PRD：

- 新增一个完整产品能力。
- 新增一个独立业务模块。
- 一个需求包含多个页面、流程或状态。
- 一个需求包含明确的业务规则。
- 一个需求会影响已有用户行为。
- 一个需求需要前端、后端、测试共同理解。
- 一个需求后续可能继续演进，需要保留产品决策依据。

以下场景通常不需要单独编写 PRD：

- 小范围文案修改。
- 单纯样式调整。
- 明确的 Bug 修复。
- 不改变产品行为的代码重构。
- 已经由现有 PRD 明确定义的小范围实现任务。

不要为了“有文档”而写 PRD。

## 3. PRD 目录规范

所有 PRD 统一放在：

```text
docs/prd/
```

按照产品领域建立二级目录：

```text
docs/prd/
├── PRD_README.md
├── system/
├── project/
├── session/
└── ...
```

目录规则：

- 二级目录表示产品领域，不表示技术模块。
- 目录名称统一使用小写英文。
- 多个单词使用 kebab-case。
- 不按照前端、后端、数据库等技术层级划分 PRD。

## 4. PRD 文件命名

文件统一使用：

```text
<feature>-v<version>.md
```

例如：

```text
user-management-v1.md
```

命名规则：

- 文件名使用小写英文。
- 多个单词使用 kebab-case。
- V1、V2 表示产品版本，不表示代码版本。
- Draft 阶段的小范围调整继续修改当前版本。
- 只有产品范围或核心行为发生明显变化时，才新增下一个版本。

## 5. PRD 状态

PRD 状态统一使用：

```text
Draft
Ready
Implementing
Done
Deprecated
```

状态含义：

- `Draft`：需求仍在讨论，可以持续调整。
- `Ready`：需求范围和核心规则已经明确，可以进入实现。
- `Implementing`：正在开发。
- `Done`：本版本已经完成并验收。
- `Deprecated`：该 PRD 已不再适用。

不要使用含义不清楚的状态名称。

## 6. PRD 顶部信息

每份 PRD 开头必须包含：

```text
状态
版本
范围
```

根据需要可以补充：

```text
负责人
目标版本
关联 Issue
关联 PR
关联设计
```

顶部信息只用于快速识别文档，不要写成复杂项目管理表格。

## 7. PRD 必须包含的内容

### 7.1 背景

说明当前发生了什么问题，以及为什么需要这个需求。

背景应该描述事实和现状，不要直接跳到解决方案。

### 7.2 产品目标

说明本次需求希望达成什么结果。

目标应该描述结果，不描述开发任务。

不要使用“优化体验”“提升效率”“更加友好”这类无法判断是否完成的空泛描述。

### 7.3 本期范围

明确本版本要完成的能力。

每一项范围都应该能够映射到实际产品行为。

### 7.4 本期不包含

明确写出与当前需求相关、但本期不做的能力。

Out of Scope 是 PRD 的必填内容。

不要依赖口头约定控制范围。

### 7.5 核心流程

存在连续操作时，必须描述主流程。

流程只描述用户行为和系统结果，不描述方法调用、类调用或代码执行链路。

### 7.6 功能需求

按照产品能力拆分功能。

每一项功能需求都必须明确系统应该表现成什么样。

不要把开发任务列表当成功能需求。

### 7.7 业务规则

所有会影响系统判断结果的规则必须显式写出。

包括但不限于：

- 默认值。
- 唯一性。
- 状态变化。
- 权限限制。
- 数量限制。
- 时间限制。
- 前置条件。
- 禁止操作。
- 异常处理。
- 边界条件。

不能把关键业务规则留给开发人员或 AI 自行猜测。

### 7.8 验收标准

PRD 必须说明什么情况下可以认为本版本完成。

验收标准应覆盖：

- 主流程。
- 关键业务规则。
- 关键异常。
- 关键边界。
- 权限差异。
- 必要的空状态。

验收标准必须可以通过产品验证或测试验证。

## 8. 按需包含的内容

以下内容不是所有 PRD 都必须存在，只在需求确实需要时添加。

### 8.1 用户与角色

当不同用户看到的内容或拥有的能力不同，需要说明角色及差异。

### 8.2 状态模型

当一个对象存在多个状态，需要说明：

- 有哪些状态。
- 初始状态是什么。
- 什么操作会改变状态。
- 哪些状态转换被禁止。

### 8.3 数据模型

PRD 只描述产品概念和关键数据关系。

可以定义对象、字段含义以及对象关系。

不要在 PRD 中展开数据库表结构、索引、ORM、Mapper 等实现细节。

### 8.4 页面与交互

当需求涉及 UI 时，需要说明：

- 页面入口。
- 页面核心区域。
- 主要操作。
- Loading。
- Empty。
- Error。
- Disabled。
- Success。

已有设计稿时直接关联设计稿，不需要在 PRD 中重复描述所有视觉细节。

### 8.5 接口契约

只有当接口本身属于产品边界或跨系统契约时才写入 PRD。

普通内部接口如何拆分，由后续技术设计决定。

### 8.6 假设

尚未验证但当前设计依赖的前提，需要明确标记为“假设”。

假设不能写成已经确认的事实。

### 8.7 风险

存在明显产品、数据、安全、兼容性或交付风险时，需要记录。

### 8.8 依赖

需求依赖其它产品能力、外部系统、设计或数据时，需要明确写出。

### 8.9 开放问题

还没有结论的问题统一放在“开放问题”。

未确认的问题不能伪装成正式需求。

## 9. 需求表达规范

### 9.1 一条需求只表达一个规则

不要在一个长段落中同时描述多个独立规则。

规则应该能够被单独理解、实现和验证。

### 9.2 使用明确词语

统一使用：

- `必须`：不可违反的要求。
- `应`：正常情况下需要满足。
- `可以`：允许但不是必需。
- `禁止`：明确不允许。

少使用：

- 尽量。
- 最好。
- 适当。
- 合理。
- 友好。
- 快速。
- 灵活。
- 等。
- 相关。

如果必须使用，应补充可以判断的条件。

### 9.3 描述结果，不描述代码

PRD 应该写：

```text
用户被禁用后禁止再次登录。
```

而不是规定：

```text
在 UserService 中增加 if 判断。
```

类名、方法名、框架、Repository、Mapper、SQL、线程模型等属于技术设计或实现阶段。

### 9.4 默认行为必须明确

存在默认值时必须写清楚。

不要让开发人员自行决定默认角色、默认状态、默认排序、默认分页大小等产品行为。

### 9.5 异常行为必须明确

不能只描述成功流程。

对用户可感知的重要失败场景，需要说明系统行为和结果。

### 9.6 边界必须明确

存在数量、长度、时间、权限、状态等边界时，需要说明允许和禁止的范围。

### 9.7 示例不能代替规则

示例只能帮助理解。

正式规则必须能够脱离示例独立成立。

## 10. 范围控制规范

PRD 的核心作用之一是控制范围。

必须遵守：

- 每个版本只解决当前确定的问题。
- V1 优先形成最小完整闭环。
- 没有真实需求的未来能力不提前加入。
- “以后可能需要”不能作为本期需求的理由。
- 能放到 Out of Scope 的内容不要偷偷进入实现范围。
- 新需求明显突破原 PRD 边界时，先更新 PRD，再修改代码。

复杂的是系统，不应该是 PRD。

## 11. PRD 与技术设计的边界

PRD 负责：

```text
Why
What
Scope
Rules
Acceptance
```

技术设计负责：

```text
How
Architecture
Module
Class
Database
Framework
Implementation
```

PRD 可以描述必要的技术约束，但不要直接代替技术设计。

如果一个技术选择不会改变产品行为，就不应该因为实现方便而写成产品需求。

## 12. PRD 与其他文档的关系

### PRD

定义产品为什么做、做什么、规则是什么、什么算完成。

### Architecture

定义系统如何组织、模块如何划分、关键技术方案如何设计。

### Code Standard

定义代码应该如何编写。

### Implementation Plan

定义当前需求准备按什么顺序实现。

### Test

验证最终实现是否符合 PRD 和接口契约。

不要让一个文档同时承担所有职责。

## 13. PRD 更新规范

PRD 不是写完后就冻结的文档。

开发过程中发现产品规则需要调整时，应先更新 PRD。

规则：

- Draft 状态可以直接调整。
- Ready 之后修改范围或核心业务规则，需要确保相关开发和测试同步知道变化。
- 小范围澄清不需要创建新版本。
- 核心产品行为发生明显改变时创建新版本。
- 已完成版本保留，不覆盖其历史产品含义。

代码不能成为产品规则的唯一来源。

## 14. 推荐 PRD 结构

新 PRD 优先使用以下结构：

```markdown
# <功能名称> PRD V1

> 状态：Draft
> 版本：V1
> 范围：<产品范围>

## 1. 背景

## 2. 产品目标

## 3. 本期范围

## 4. 本期不包含

## 5. 用户与角色

## 6. 核心流程

## 7. 功能需求

## 8. 业务规则

## 9. 状态与边界

## 10. 页面与交互

## 11. 风险、依赖与开放问题

## 12. 验收标准

## 13. 后续演进
```

不相关的可选章节可以删除。

不要为了满足模板而保留空章节。

## 15. PRD Review Checklist

PRD 进入 `Ready` 前至少检查：

- 是否说清楚了为什么做。
- 是否存在明确的产品目标。
- 是否明确了本期范围。
- 是否明确了 Out of Scope。
- 是否存在没有说明的默认行为。
- 是否存在开发人员需要自行猜测的业务规则。
- 是否描述了关键异常和边界。
- 是否存在无法验证的模糊词语。
- 是否把技术实现误写成产品需求。
- 是否有未解决问题被当成正式需求。
- 是否有明确的验收标准。
- 产品、开发、测试或 AI 是否能够基于同一份 PRD 得到基本一致的理解。

如果仍然需要大量猜测，这份 PRD 还没有准备好进入开发。

## 16. Yakable PRD 原则

Yakable 的 PRD 不追求篇幅。

追求的是：

```text
问题清楚
范围清楚
规则清楚
边界清楚
验收清楚
```

能确定的事情写成规则。

不能确定的事情写成开放问题。

本期不做的事情明确排除。

不要把产品决策留给实现阶段临时决定。

> PRD 的价值不是记录更多信息，而是减少实现时需要猜测的信息。
