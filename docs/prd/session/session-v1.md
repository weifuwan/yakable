# Yakable Session PRD V1

> 状态：Draft  
> 版本：V1  
> 范围：Session

## 1. 背景

Project 解决“这个工作是什么、属于谁、从哪里继续”，Session 需要继续解决“在这个 Project 里如何持续完成一段对话”。  
如果 Session 的创建、发送、停止、失败恢复和上下文规则不明确，同一个 Project 内的对话行为就会由前端、后端和模型各自猜测。  
Session V1 先建立一条稳定、可恢复、可持续发送消息的对话闭环，不提前引入多会话管理和 Agent 能力。

## 2. 产品目标

Session V1 需要让用户进入 Project 后能够持续发送 Prompt、接收流式 AI 回答，并在停止、失败、刷新或重新进入后继续当前对话。  
系统需要明确一轮用户交互什么时候成立、什么时候允许下一轮、哪些历史内容进入上下文，以及对话过长时系统如何自动处理。  
这一版本只解决“一段持续对话如何可靠进行”，不扩展成通用 Agent Runtime。

## 3. 本期范围

每个 Project 在 V1 产品中只使用创建 Project 时自动建立的初始 Session。  
用户不能主动创建第二个 Session，也不提供 Session 列表、切换、关闭、删除和重命名。  
Project 创建完成后，用户直接进入这个初始 Session，并在其中持续完成后续对话。

Session 内由多轮用户交互组成。  
用户每发送一次 Prompt，系统建立一轮新的交互；这一轮包含用户输入、AI 执行状态，以及有结果时的 Assistant 内容。  
Turn 和 Message 是 Session 内表达一轮交互和消息的必要概念，V1 不为它们单独建立产品入口。

Session 必须继承所属 Project 的访问边界。  
用户只能访问自己 Project 下的 Session；知道其他用户的 Project ID、Session ID、Turn ID 或 Message ID，都不能绕过 Project 的归属限制读取或操作对应对话。

## 4. 本期不包含

V1 不包含用户主动创建第二个 Session、Session 列表、Session 切换、Session 删除、归档、关闭和重命名。  
V1 不包含消息删除、消息编辑、对历史消息建立分支，以及基于旧消息重新生成一条平行对话。  
这些能力出现真实需求后再单独设计。

V1 不包含 Agent Planning、Tool Call、工作流编排、人工审批和多步骤任务执行。  
V1 不包含跨 Session 长期记忆、自动总结、向量检索、知识库和跨 Project 上下文。  
上下文只来自当前 Session 已经存在的对话历史。

V1 不为 Session 设计用户可操作的生命周期状态。  
“等待执行、生成中、成功、失败、停止”属于一轮交互的执行状态，不属于 Session 本身。  
Session 只要所属 Project 可访问，就应能够继续进入和使用。

## 5. 功能与业务规则

### 5.1 Session 是什么

一个 Session 表示用户在同一个 Project 中持续进行的一段对话。  
V1 中 Project 创建时必须同时建立唯一的初始 Session，用户进入 Project 后直接进入这个 Session。  
Session 不等同于某一次模型调用，也不因为某一轮生成失败或停止而结束。

初始 Session 标题使用 Project 名称。  
V1 中 Session 标题不会因为后续 Prompt 或模型回答自动变化，也不支持用户手动修改。  
Session 标题只用于当前对话界面的识别，不形成独立的 Session 管理能力。

### 5.2 发送一轮对话

用户只有在当前 Session 没有正在执行的交互时，才可以发送新的非空 Prompt。  
用户提交后，界面应立即反馈这条用户输入并进入生成状态；同一 Session 同一时间最多只能有一轮正在执行。  
如果前一轮仍处于等待执行或生成中，系统必须阻止再次创建新的并发交互。

只有当用户 Message 已经成功持久化后，这一轮交互才算正式成立。  
一轮交互成立后，即使后续模型调用失败或用户停止生成，已经保存的用户 Message 也不能被删除或回滚。  
如果请求在用户 Message 建立前失败，用户应能够保留原输入并重新发送。

### 5.3 Session 最近活动

Session 的最近活动由真实用户交互决定。  
当一条新的用户 Message 成功持久化时，Session 的最近活动时间必须更新；仅打开页面、刷新页面或读取历史消息不能改变最近活动时间。  
AI 回答成功、失败或用户停止生成，不应在同一轮中再次改变 Session 的最近活动时间。

Project 的 Recent Projects 排序和最近 Session 判断，应使用这一 Session 最近活动语义。  
因此用户发送新 Prompt 后，对应 Project 可以立即成为最近活动 Project，不需要等待 AI 回答完成。  
如果模型随后失败，最近活动顺序也不能回退。

### 5.4 模型选择

Project 创建时选择的模型作为初始 Session 第一次交互使用的模型。  
用户在后续每次发送 Prompt 前可以切换模型；本次选择只决定这一轮实际调用的模型，不把模型永久绑定到 Project。  
同一个 Session 的不同交互可以使用不同模型。

当一轮新的用户 Message 成功建立时，本轮选择的模型成为该 Session 下一次打开或发送时的默认选择。  
用户仅在界面中切换模型但没有发送 Prompt 时，不应改变已经持久化的 Session 默认模型。  
刷新页面后，模型选择器应恢复到最近一次已经建立交互所使用的模型。

### 5.5 流式回答与生成状态

一轮交互建立后，界面应明确展示正在生成，并持续显示已经收到的 Assistant 内容。  
在第一段 Assistant 内容返回前，可以展示明确的 Thinking 状态；开始收到内容后，应直接展示流式回答。  
用户不需要等待完整回答结束后才看到结果。

一轮交互需要能够区分等待执行、生成中、成功、失败和已停止。  
成功表示本轮得到正常 Assistant 结果；失败表示本轮执行无法正常完成；已停止表示用户主动结束本轮生成。  
这些状态必须能够在刷新页面后从持久化数据恢复，不能只存在于浏览器内存。

### 5.6 停止生成

生成过程中用户可以主动停止当前一轮。  
停止后，已经持久化的用户 Message 必须保留；已经产生的 Assistant 部分内容如果非空，也应保留并在刷新后继续可见。  
系统不应因为停止而删除整轮对话。

停止完成后，本轮进入终态，Session 应立即允许用户发送下一条 Prompt。  
如果停止发生时还没有产生 Assistant 内容，不需要为了保持结构而创建一条空的 Assistant Message。  
已停止的内容不自动重新生成，用户需要通过新的 Prompt 继续对话。

### 5.7 失败与恢复

模型调用失败时，已经保存的用户 Message 必须保留，并向用户显示明确的失败状态。  
失败不能删除 Session、Project 或之前已经成功的历史消息。  
失败的交互进入终态后，用户可以继续发送下一条 Prompt。

刷新页面、切换页面再返回或浏览器重新打开后，系统必须从持久化数据恢复 Session 历史和当前交互状态。  
如果刷新时存在等待执行或生成中的交互，系统不能因为页面重新加载而重复创建一轮新的交互。  
服务端中断后的执行也不能无限停留在“生成中”，最终必须恢复执行或进入明确终态。

### 5.8 历史消息展示

进入 Session 时默认加载最近 50 条 Message，并按照真实对话顺序展示。  
如果历史消息超过 50 条，用户向上查看时可以继续加载更早的消息；进入页面时不一次性加载整个 Session 的全部历史。  
重新加载较早消息不能打乱现有消息顺序，也不能重复展示同一条 Message。

正在生成的 Assistant 内容应始终出现在对应用户 Message 之后。  
停止后保留的部分回答、失败前已经持久化的内容以及历史成功回答，都应在重新进入 Session 后保持稳定顺序。  
消息展示分页只影响界面加载，不改变发送给模型的上下文规则。

### 5.9 LLM 上下文

每轮模型调用的上下文只能来自当前 Session，禁止自动混入其他 Session 或其他 Project 的历史。  
当前用户 Prompt 必须完整参与本轮上下文，系统不能为了塞入更多历史而静默截断用户本次输入。  
历史过长时，系统应自动从最早的历史开始裁剪，不要求用户手动清理上下文。

历史上下文优先使用已经成功完成的交互。  
用户主动停止且已经保留非空 Assistant 内容的交互，可以继续作为后续上下文的一部分。  
失败且没有有效 Assistant 回答的交互，不应被当作一轮完整历史继续发送给模型。

系统应根据当前选择模型可用的 Context 自动控制历史范围。  
如果移除历史后，当前用户 Prompt 本身仍然超过模型能够处理的范围，本轮应明确失败并提示输入过长，不能静默截断当前 Prompt 后继续生成。  
V1 不进行自动总结、长期记忆或跨 Session 压缩。

### 5.10 页面交互与恢复

进入 Session 时，历史数据加载完成前不能短暂展示上一 Session 或旧页面残留内容。  
加载成功后默认定位到最新消息附近；用户主动向上阅读历史时，新生成内容不能强制把页面不断拉回底部。  
当用户需要返回最新内容时，应提供明确的回到底部入口。

发送成功后输入框应清空；如果本轮在用户 Message 持久化前创建失败，原 Prompt 应保留供用户重试。  
生成期间发送入口切换为停止能力，避免同一 Session 产生并发交互。  
失败和停止后，输入区域恢复可用，用户可以继续下一轮。

## 6. 验收标准

用户创建 Project 后能够立即进入初始 Session，并看到首次 Prompt 形成的第一轮对话。  
用户可以在同一 Session 中连续发送多轮 Prompt，每次只能有一轮处于等待执行或生成中；上一轮成功、失败或停止后才能开始下一轮。  
刷新页面后，历史 Message、模型选择和交互状态能够正确恢复，不重复创建 Turn 或 Message。

用户发送 Prompt 后，用户 Message 成功持久化即更新 Session 最近活动时间，对应 Project 可以立即回到 Recent Projects 顶部。  
AI 回答完成、失败或停止不会再次改变同一轮的最近活动时间。  
仅查看或刷新 Session 不会改变 Recent Projects 排序。

用户可以在每轮发送前切换模型，本轮实际使用所选模型；发送成功建立交互后，该模型成为 Session 下一轮默认模型。  
不同轮次允许使用不同模型，刷新后恢复最近一次已经建立交互所使用的模型。  
用户只切换模型但没有发送时，不改变持久化默认模型。

用户停止生成后，已保存的用户 Message 和已有的非空部分回答仍然存在，Session 可以继续发送下一轮。  
模型失败后，用户 Message 和已有历史不会丢失，并能够继续对话。  
正在执行的交互在刷新或服务恢复后不会永久卡在生成状态。

进入长 Session 时只加载最近 50 条 Message，并能够继续向上加载更早历史。  
历史展示顺序稳定且不重复；用户阅读旧消息时不会被流式输出强制拉回底部。  
回到底部入口能够让用户快速返回最新内容。

上下文只使用当前 Session；历史超过当前模型可处理范围时自动裁剪最早历史。  
当前 Prompt 不会被静默截断；如果当前 Prompt 本身超出模型处理范围，应明确失败。  
失败且没有有效 Assistant 回答的交互不会作为完整历史进入后续上下文。

V1 不出现第二个 Session 的创建、Session 列表与切换、Session 删除或归档、消息编辑删除、对话分支、Agent Tool 和跨 Session 记忆。  
以上主流程、停止与失败边界、恢复行为、模型规则、历史加载和上下文规则全部满足后，Session V1 才算完成。

## 7. 后续演进

未来如果用户确实需要在同一个 Project 中并行维护多条对话，再增加 Session 创建、列表、切换、重命名和管理能力。  
如果出现 Agent、Tool、工作流或长任务需求，再重新定义一轮交互的执行模型，而不是让 V1 Session 提前承担这些职责。  
跨 Session 记忆、自动总结和更复杂的 Context Harness 也应在真实需求出现后单独设计。
