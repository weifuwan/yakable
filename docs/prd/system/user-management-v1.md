# Yakable 用户管理 PRD V1

> 状态：Done  
> 版本：V1  
> 范围：系统用户管理

## 1. 背景

Yakable 已经具备 Project、Session、Turn、Message 等基础业务能力，但系统目前还没有正式的用户体系。  
这会导致系统无法稳定回答“当前是谁在使用 Yakable”，也无法对用户进行统一管理。  
V1 先建立最小可用的用户管理闭环，不提前引入团队、多租户和复杂权限体系。

## 2. 产品目标

用户管理 V1 需要让用户能够使用自己的账号登录 Yakable，并让系统能够识别当前登录用户。  
管理员需要能够创建、维护、启用和禁用用户，普通用户需要能够维护自己的基础信息和密码。  
这一版本只解决“你是谁、你能不能登录、你是不是管理员”三个问题。

## 3. 本期范围

本期包含用户登录、退出登录、当前用户信息、用户列表、创建用户、编辑用户、启用和禁用用户。  
同时包含用户修改自己的密码、管理员重置用户密码，以及首次部署时初始化第一个管理员。  
用户管理需要形成从“创建账号 → 登录 → 使用 → 管理”的完整闭环。

本期不包含公开注册、邮件邀请、邮箱登录、找回密码、OAuth、GitHub 登录、Google 登录、SSO、LDAP 和 MFA。  
本期也不包含 Workspace、Tenant、Team、Organization、Membership、RBAC、自定义角色、用户组和部门。  
这些能力只有在 Yakable 出现真实业务需求后再单独设计。

## 4. 用户、角色与状态

系统当前只有一种账号类型：User。每个 User 必须拥有唯一的用户名和展示名称，并可以选填邮箱和头像。  
用户名是 V1 唯一的登录标识，创建后禁止修改；用户名按不区分大小写的方式保持唯一。  
邮箱只作为基础资料保存，可以为空；V1 不使用邮箱进行登录、验证或找回密码。

V1 只保留 `ADMIN` 和 `USER` 两种角色。  
ADMIN 可以管理系统用户；USER 可以正常使用 Yakable、查看和维护自己的信息。  
V1 不设计独立的 Role、Permission 或用户与角色关系模型。

用户状态只保留 `ACTIVE` 和 `DISABLED`。  
ACTIVE 用户可以正常登录和使用 Yakable；DISABLED 用户禁止继续使用系统。  
用户被禁用后，已有登录状态应立即失效，且在重新启用前不能再次登录。

系统不提供物理删除用户的能力。  
已经创建的用户只能启用或禁用，避免用户与 Project、Session、Message 等历史数据建立关系后出现数据归属丢失。  
因此 V1 统一使用“禁用”代替“删除”。

## 5. 功能与业务规则

### 5.1 登录与退出

登录页面只提供用户名和密码登录。  
用户名或密码错误时，统一提示“用户名或密码错误”，不能分别暴露用户不存在或密码错误。  
账号被禁用时，应明确提示“当前账号已被禁用”。

登录成功后，系统需要持续识别当前用户，并在界面中提供当前用户的名称、头像和角色信息。  
用户主动退出登录后，当前登录状态必须立即失效。  
未登录用户访问需要登录的页面时，应进入登录流程。

### 5.2 用户列表

只有 ADMIN 可以进入用户管理。  
用户列表需要展示用户、用户名、邮箱、角色、状态、最近登录时间和创建时间，并提供对应管理操作。  
列表支持按用户名、名称或邮箱搜索，并支持按角色和状态筛选。

用户管理入口放在系统设置中，页面保持简单，不增加用户统计、登录趋势、角色统计或用户画像。  
V1 的用户管理页面只负责管理账号，不承担运营分析能力。  
普通 USER 不应看到或访问用户管理能力。

### 5.3 创建用户

ADMIN 可以创建新的用户。  
创建时必须填写用户名、名称、角色和初始密码，邮箱和头像可以为空。  
未主动选择时，角色默认为 USER，状态默认为 ACTIVE。

用户名必须全局唯一，且唯一性不区分大小写。  
如果用户名已经存在，系统应阻止创建并明确提示用户名已存在。  
创建成功后，用户可以直接使用用户名和初始密码登录，不发送邀请邮件。

### 5.4 编辑用户

ADMIN 可以修改用户的名称、邮箱、头像和角色。  
用户名创建后禁止修改，密码也不能通过普通编辑用户操作直接修改。  
密码修改和密码重置使用独立操作。

管理员可以修改自己的基础信息，但不能禁用自己，也不能把自己的角色从 ADMIN 修改为 USER。  
系统始终必须保留至少一个 ACTIVE ADMIN。  
最后一个可用管理员禁止被禁用，也禁止被降级为 USER。

### 5.5 启用与禁用

ADMIN 可以启用或禁用其他用户。  
用户被禁用后应立即退出当前登录状态，后续请求也不能继续以该用户身份使用 Yakable。  
重新启用后，用户可以继续使用原用户名和密码登录。

禁用用户不删除任何历史数据。  
用户列表中仍然需要保留被禁用用户，并清楚显示 DISABLED 状态。  
管理员可以随时重新启用该用户。

### 5.6 修改和重置密码

用户可以修改自己的密码，修改时必须先验证当前密码。  
新密码长度必须为 8～64 个字符，V1 不要求必须同时包含大小写字母、数字或特殊字符。  
新密码与确认密码不一致时，禁止提交。

用户成功修改自己的密码后，原有登录状态全部失效，需要使用新密码重新登录。  
ADMIN 可以为其他用户重置密码，重置时不需要知道用户原密码。  
管理员重置密码成功后，该用户已有登录状态同样全部失效。

### 5.7 首个管理员

系统第一次部署且不存在任何用户时，必须能够初始化第一个 ADMIN。  
首个管理员由部署方提供初始账号和密码，系统不开放公共注册入口。  
系统已经存在用户后，不得再次通过初始化流程创建首个管理员。

## 6. 验收标准

用户管理 V1 完成后，ADMIN 能够登录系统、创建 USER，并在用户列表中完成搜索、编辑、禁用和重新启用。  
新建 USER 能够使用初始密码登录、查看自己的信息并修改密码；修改密码后需要重新登录。  
普通 USER 不能访问用户管理能力。

用户名重复时必须阻止创建，用户名或密码错误时不能暴露具体失败原因。  
DISABLED 用户不能继续使用已有登录状态，也不能重新登录；重新启用后可以恢复登录。  
管理员不能禁用或降级自己，最后一个 ACTIVE ADMIN 也不能被禁用或降级。

管理员能够重置其他用户密码，重置后该用户原有登录状态全部失效，并只能使用新密码重新登录。  
系统首次部署时能够初始化第一个管理员，已有用户后不会重复初始化。  
以上主流程、关键规则和异常边界全部满足后，用户管理 V1 才算完成。

## 7. 后续演进

未来如果出现一个用户属于多个团队、多人共同管理一个项目、不同团队需要数据隔离等真实需求，再引入 Workspace、Membership 和更完整的权限模型。  
Project、Session 等业务数据与用户归属的进一步绑定，也在对应业务需求出现时单独设计。  
V1 不为了未来可能发生的需求提前增加复杂度。
