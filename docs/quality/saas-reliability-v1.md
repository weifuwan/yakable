# Yakable SaaS Reliability V1

> 状态：Draft  
> 版本：V1  
> 范围：当前 SaaS 核心链路  
> 原则：不新增产品功能，只提高稳定性、可用性和性能

## 1. 目标

Yakable 当前阶段不以功能数量为目标。

现阶段优先保证：

- 已有功能长期稳定运行。
- 用户已经提交的数据不丢失。
- 同一个业务操作不会被重复执行。
- 异常发生后能够恢复或进入明确终态。
- 外部模型、网络和浏览器异常不能破坏核心数据。
- 性能问题通过真实数据定位，不提前堆复杂架构。

当前核心链路是：

```text
User
  ↓
Project
  ↓
Session
  ↓
Turn
  ↓
Message
  ↓
LLM
```

本规范只约束这条已经存在的链路，不扩展 Workspace、Agent、Tool、Workflow 等新产品能力。

## 2. 稳定性底线

以下问题属于不能接受的 SaaS 可靠性问题：

- 已经成功提交的数据因为后续异常被删除或回滚。
- 同一个请求因为重试、刷新或恢复被重复创建。
- Turn 永久停留在 PENDING / RUNNING，没有恢复路径。
- 一个 Turn 已经进入终态后又被其他迟到事件覆盖。
- 浏览器断开或 SSE 断开被错误解释成业务 Stop。
- 外部 LLM 异常导致 Project、Session 或历史 Message 丢失。
- 单个用户或单个请求可以无限占用线程、连接、内存或数据库资源。
- 未授权用户可以通过猜测 ID 读取或操作其他用户数据。

发现以上问题时，优先修复，不继续增加功能。

## 3. 数据一致性

数据库是 Project、Session、Turn、Message 状态的最终事实来源。

关键业务数据不能只存在于浏览器状态或 JVM 内存中。

需要原子成立的数据，应放在同一个数据库事务中完成。

外部 LLM 调用不得放在数据库事务中。

异步执行只能在需要持久化的业务数据成功提交后启动。

一轮交互已经通过 USER Message 正式成立后，后续模型失败、Stop 或网络异常不能回滚该 USER Message。

状态变化必须通过带前置状态条件的更新完成，不能直接无条件覆盖。

Flyway Migration 遇到无法安全判断的数据时应明确失败，禁止静默猜测或自动修复未知历史数据。

## 4. 并发与重复执行

同一个 Session 同一时间最多只能存在一个 PENDING / RUNNING Turn。

并发限制必须由服务端和数据库共同保证，不能只依赖前端按钮禁用。

Turn 的 SUCCEEDED、FAILED、STOPPED 是互斥终态。

重复 Stop、迟到 Complete、迟到 Failure 和恢复任务都不能覆盖已经确定的终态。

恢复任务必须继续执行原 Turn，禁止因为恢复重新创建 Turn 或 USER Message。

同一个业务请求即使因为浏览器重试、网络重连或后台恢复被再次触发，也不能造成重复业务结果。

不能把 JVM 内存锁作为跨实例正确性的唯一保证。

## 5. 异步执行与 Streaming

Turn 执行生命周期与 SSE 连接生命周期必须分离。

SSE 只负责观察执行结果，不拥有 Turn 生命周期。

浏览器刷新、页面切换、SSE timeout 和网络断开不能自动 Stop Turn。

用户显式 Stop 才能触发 STOPPED。

重新进入页面时，应恢复同一个 PENDING / RUNNING Turn，禁止自动重新提交原 Prompt。

后台服务恢复后，RUNNING Turn 不能永久卡住。

恢复机制必须有明确的超时、批次和终止条件。

Streaming 已经产生的非空 Assistant 内容，在 Stop 或 Failure 时应按产品规则持久化。

## 6. 外部依赖

数据库、LLM Provider 和外部 HTTP 调用都必须设置明确超时。

禁止无限等待外部依赖。

重试只能用于能够证明安全的场景。

不能因为“可能失败”就给所有调用统一增加自动重试。

涉及创建、状态修改或有副作用的操作，在没有幂等保证前禁止自动重试。

外部 Provider 失败必须转换成明确的系统错误，不能让异常直接破坏核心业务状态。

Provider 不可用时，只影响对应 Turn，不应影响已有 Project、Session 和历史 Message。

## 7. 资源边界

线程、数据库连接、HTTP 连接、SSE 连接、内存缓冲和任务队列都必须有明确边界。

禁止业务代码创建不受管理的线程池。

后台任务统一通过项目已有线程能力执行。

SSE 连接结束、超时或异常后必须释放 listener 和相关资源。

Streaming buffer 不能无限增长。单条 Message 必须同时存在应用层大小边界和与之匹配的数据库字段容量，不能只依赖数据库写入失败兜底。

Message 页面加载必须分页，不能默认一次加载整个 Session 历史。Session 首屏、增量查询和 Context 构建都必须保持数据库读取有界，不能先全量读取再在 JVM 中裁剪。

Context 必须受模型 Token Budget 约束，并从最近历史向更早分批读取；达到预算后停止继续访问更老数据。

恢复任务必须限制单次处理数量，不能一次扫描并执行全部历史任务。

任何可能随用户数量持续增长的内存结构，都必须有明确释放条件。

## 8. 安全边界

所有用户数据访问必须以当前认证用户为边界。

Project Ownership 是 Session、Turn、Message 访问控制的根边界。

知道 Project ID、Session ID、Turn ID 或 Message ID 不能绕过 Ownership。

浏览器 Cookie 鉴权场景必须保持 CSRF 防护。

密码、API Key、Session Token、Cookie 等敏感信息禁止写入日志。

Prompt 和模型回答默认不作为普通运行日志输出。

错误响应不能暴露内部密钥、数据库信息和不必要的堆栈细节。

## 9. 可观测性

线上问题必须能够通过日志和指标定位，而不是依赖复现猜测。

关键日志应能够关联：

- requestId。
- userId。
- projectId。
- sessionId。
- turnId。

没有对应值时不要为了统一格式强行补空字段。

日志记录状态变化和失败原因，不记录完整 Prompt、完整模型回答和敏感信息。

至少需要能够观察以下运行指标：

- HTTP 请求量、错误率和延迟。
- 当前活跃 SSE 连接数。
- PENDING / RUNNING Turn 数量。
- Turn 成功、失败、Stop 和恢复数量。
- LLM 调用耗时和失败率。
- 数据库连接池使用情况。
- 线程池 active、queue 和 rejection。
- JVM 内存与 GC。

指标用于定位问题，不为了“指标完整”增加无价值埋点。

## 10. 性能原则

性能优化必须先有数据。

禁止因为担心未来性能问题，提前引入 Redis、MQ、分布式锁、缓存层或复杂异步架构。

当前阶段优先建立性能基线，而不是先设想优化方案。

重点观察：

- 登录和普通查询接口 P95。
- Recent Projects 查询 P95。
- Session 首次加载 P95。
- Message 分页查询 P95。
- 创建 Turn 到 USER Message 持久化的耗时。
- LLM 首个有效流式内容等待时间。
- Context 构建耗时。
- 并发 SSE 连接资源占用。
- 数据库连接池峰值使用率。
- 线程池峰值 active 和 queue。

没有真实测试数据前，不写死没有依据的性能目标。

发现瓶颈后，先优化当前实现，再决定是否需要新增基础设施。

## 11. 测试要求

可靠性问题必须通过测试保护已经确定的行为。

Service 重点保护：

- 状态变化。
- 并发限制。
- Stop / Failure。
- Recovery。
- Context。
- 异常边界。

Controller 重点保护：

- HTTP Contract。
- 权限。
- CSRF。
- SSE Contract。

DAO Integration Test 重点保护：

- 数据库约束。
- 条件更新。
- 并发相关 SQL。
- Flyway Migration。
- 真实事务行为。

Model Plugin 不调用真实第三方服务。

修复数据丢失、重复执行、状态错误、权限绕过和恢复失败后，必须增加能够防止回归的测试。

测试遵循根目录 `BACKEND_TEST_README.md`，不为了覆盖率增加无业务价值测试。

## 12. 发布前检查

每次涉及核心链路的修改，至少确认：

- 正常流程是否仍然成立。
- 请求重复执行是否安全。
- 中途失败是否会留下错误数据。
- 服务重启后是否能够恢复。
- 浏览器断开是否影响后台业务状态。
- 终态是否可能被迟到事件覆盖。
- 权限边界是否仍然存在。
- 新代码是否增加无限资源占用风险。
- 是否有对应测试保护关键行为。
- 是否真的需要新增组件或基础设施。

存在明确的数据丢失、权限绕过、重复执行、永久卡死或资源泄漏风险时，不应发布。

## 13. 当前阶段不做

没有真实问题前，不因为“以后可能需要”提前增加：

- Redis。
- MQ。
- 分布式锁。
- 微服务拆分。
- 通用任务调度平台。
- 通用重试框架。
- 通用缓存层。
- 复杂状态机框架。
- 额外 Manager / Handler / Coordinator 等中间层。

真正出现单机无法解决的问题后，再基于证据升级架构。

## 14. Review 方法

后续 Reliability Review 只围绕已经存在的核心链路检查。

每个问题按以下方式记录：

```text
问题
→ 触发条件
→ 可能后果
→ 当前保护
→ 缺口
→ 最小修复
→ 验证方式
```

优先处理会造成：

```text
数据丢失
> 权限问题
> 重复执行 / 状态错误
> 永久卡死
> 资源泄漏
> 明显性能瓶颈
> 一般代码质量问题
```

不要为了 Review 数量制造问题。

## 原则

**先稳定，再优化，再扩展。**

**能用当前架构解决的问题，不新增基础设施。**

**能用明确规则解决的问题，不交给运行时猜。**

**没有数据证明是性能问题，就先测，不先改。**

**SaaS 的价值不是功能多，而是用户每天都能稳定地用。**
