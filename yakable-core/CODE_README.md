# yakable-core 编程规范

本规范适用于 `yakable-core` 下所有 Java 代码，只约束通用编码规则，不包含具体业务规则。

## 代码格式

1. 简单方法声明、构造方法、record 声明和方法调用能一行写完就写一行。

2. 只有参数较多或单行明显过长时才允许换行，禁止为了一个参数做无意义换行。

3. 换行后保持结构紧凑、统一。同一组参数、同一段链式调用使用一致的缩进方式。

4. 禁止把 `) {` 单独悬空。多行方法声明的最后一个参数应与右括号、左花括号保持在同一行。

5. 方法调用同样遵循紧凑原则，禁止把右括号单独拆成一行。

6. 链式调用只有在单行明显过长时才换行，换行后每一级调用保持同一缩进层级。

7. 禁止为了“看起来整齐”增加没有必要的空行、换行和缩进层级。

## 公共工具

8. Core 需要通用能力时优先复用 `yakable-common` 已有工具，禁止在 Core 中重复实现相同能力。

9. 对象转换、时间、ID、线程等公共处理优先使用 Common 已有统一能力；Common 已经提供的能力不得在 Core 中重新封装一层。

10. 字符串判空、截断、标准化、格式处理等优先使用统一字符串工具，禁止在不同 Core 类中重复编写相同字符串处理逻辑。

11. JSON 序列化、反序列化、节点读取等优先使用统一 JSON 工具，禁止在 Core 业务代码中散落创建和配置 JSON 处理对象。

12. Common 暂无对应工具但该能力存在复用价值时，优先补充到 Common，再由 Core 使用；只有当前类独有且非常简单的逻辑才保留为私有方法。

## Lombok

13. 能通过 Lombok 明确减少样板代码时优先使用 Lombok，禁止手写大量重复的 Getter、Setter、构造方法、equals、hashCode、toString 等代码。

14. Lombok 只用于减少样板代码，不为了使用 Lombok 改变原本清晰的数据结构；不可变数据使用 record 已经足够简洁时继续使用 record。

15. 优先使用职责明确的 Lombok 注解，避免为了省代码无脑使用包含过多隐式行为的组合注解。

## Core 边界

16. Core 保持纯 Java 运行时契约，不参与 Spring / Spring Boot 容器装配。

17. Core 中禁止使用 Spring / Spring Boot 组件、配置和依赖注入注解，包括 `@Component`、`@Service`、`@Configuration`、`@Bean`、`@Value`、`@Autowired`、`@ConfigurationProperties` 等。

18. Core 中同样不使用 `@Resource` 等容器依赖注入方式。对象依赖通过普通 Java 参数、构造方法或明确的接口关系表达。

19. Spring Bean 创建、配置读取、Provider 装配等运行时工作放在 Boot 或 Service，禁止下沉到 Core。

## 代码结构

20. 一个类只承担明确职责，能在当前类内清晰表达的逻辑不要提前拆成新的 Manager、Helper、Handler、Adapter 等中间层。

21. 没有真实复用场景时，不为了减少少量重复代码提前抽象公共类或公共接口。

22. 私有实现细节优先使用 `private` 方法收敛，只有形成稳定公共能力后再向外抽取。

23. 命名直接表达职责和语义，禁止使用含义模糊的 `Manager`、`Processor`、`Handler` 等名称掩盖实际职责。

24. 能直接返回表达的结果不增加无意义的临时变量；能直接调用已有能力不增加一层无意义转发。

## 注释

25. 对外公开的接口、类和核心方法必须有必要的 Javadoc，说明职责、输入输出语义或关键边界。

26. 注释重点说明“为什么这样设计”“有什么约束”“调用方需要知道什么”，禁止逐行复述代码已经表达清楚的内容。

27. 接口已经完整说明方法语义时，实现类对应方法不重复复制相同注释。

28. 私有方法、简单字段和一眼能看懂的代码不强制写注释，禁止为了注释数量增加无意义说明。

29. 复杂规则、兼容性处理、非直观判断必须写必要注释，避免后续修改时只能通过猜测理解原因。

30. 注释必须与当前实现保持一致；代码行为变化时同步更新注释，过期注释必须删除。

## 基本原则

**优先复用，减少重复。**

**保持简单、紧凑、统一。**

**没有真实问题之前，不提前增加抽象。**
